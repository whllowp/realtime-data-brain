## 1. 为什么选 SMD，以及它的局限

**数据集：SMD / ServerMachineDataset**（KDD 2019 OmniAnomaly 论文数据集，[仓库](https://github.com/NetManAIOps/OmniAnomaly)）

| 项 | 内容 |
|---|---|
| 内容 | 28 台服务器 × 38 维系统指标（CPU、load、内存、磁盘、网络），每分钟一个采样 |
| 标注 | `test_label/` 逐点 0/1 人工标注；`interpretation_label/` 另外标出**故障根因维度** |
| 本次使用 | `machine-1-6`：23,689 行采样，3,708 个异常点（15.65%），故障区间最长 **3,161 分钟**；`machine-2-2`：23,700 行，2,833 异常点（11.95%） |
| 获取 | `python scripts/real_data/fetch_smd.py [--machine machine-2-2]`（数据落在 `data/smd/`，已 gitignore） |

**必须说明的局限（会直接影响结论的解读）：**

1. **SMD 是主机遥测，不是服务遥测。** 没有 QPS、错误数、延迟。出厂 catalog 的 13 个指标源里，**只有 2 个**（`cpu_util`、`memory_util`）能被填充，**11 个填不上**。这是真实的覆盖缺口，不是细节。
2. **数值是数据集作者做过 per-column min-max 归一化的**，所以是"相对水平"而非物理单位。单调变换不改变 AUC 排序，但不能把 `0.98` 读成"98% CPU"。
3. **列语义按 SMD 文档假定**：本机第 8 列恒为 0，说明列的排布可能与文档有出入；检测只用数值和基线，所以列名错了只会影响文字标签，不影响测量本身。
4. 单机、300 秒窗口、标签为点级（窗口内任一点异常即记异常）。后续优化把窗口改为 600 秒以获得 2 倍速度，数字见 OPTIMIZATION_LOG。

## 3. 四个发现

### 3.1 架构对"持续型异常"结构性失明（最严重）

同一批窗口，同一批特征，只改**求值方式**：

| 求值方式 | 8 特征平均 AUC |
|---|---|
| **level**（绝对水平） | **0.8152** |
| ratio（相对 30 窗滚动基线） | 0.4929 |
| delta（与基线之差） | 0.4733 |

单项更极端，例如 `mem_free`：level **0.8757** vs ratio **0.3650**。

**机制**：`BaselineTracker` 用 30 窗滚动中位数作基线。SMD 的故障区间常持续几十到上千分钟（最长 3,161 分钟），一旦故障持续时间超过基线窗口，基线会把故障**吸收成新常态**，比值回到 1.0 —— 于是 `CPU 1.03x its baseline` 是**正确的比较**，却恰好藏住了故障。

**结论**：`brian` 出厂的检测机制是**尖峰检测器**，不是事故检测器。我的合成场景每个只持续 1–2 个窗口，所以从未暴露这个问题。这是本次外部验证最重要的发现。

### 3.2 在这个数据集上，一行规则打败了模型

- 单条 CPU 水平阈值：recall **0.804** @ FPR 0.087（AUC 0.900）
- Laya（出厂形态，扫点后）：recall **0.735** @ FPR 0.095（AUC 0.862）

**当问题退化成"某个数是不是偏高"时，阈值告警才是对的工具，421M 参数没有增量价值。** Laya 的价值必须来自阈值表达不了的判断 —— 多信号、分类、带条件的处置 —— 而这一类问题 SMD 并不包含。

### 3.3 "状态更完备"反而更差

| 喂进状态的信息量 | AUC |
|---|---|
| 8 指标 + 比值 | 0.515 |
| 3 指标 + 比值 | 0.692 |
| 2 指标，裸百分比 | 0.862 |
| 1 指标（数值对照，非模型） | 0.900 |

信号越少越强，反而越好。原因有二，都被量化了：新增维度本身较弱（网络类 level AUC 仅 0.60–0.65），会**稀释**那一个强信号；把它们表述成"相对基线的倍数"，又引入了 3.1 所述的失明。

这与渲染器实验的结论同源 —— **更多信息不等于更多证据** —— 但这次是在我没写过的数据上复现的。

### 3.4 默认阈值在真实数据上完全不触发

出厂形态在 0.5 阈值下 **4,708 个窗口全部 `suppress`**（它是"高置信度地认为正常"），但同一批概率的 AUC 是 0.862。排序可用、标定不可用、阈值位置错 —— 三件事是独立的。这印证了 `GateThresholds` 里"阈值必须按域扫出来、并说明在哪把尺子上"的设计，同时也说明：**换一个数据域就必须重新扫阈值，否则系统看起来是"静默无误"的**。

## 4. 复现

```powershell
# 1. 取数（需要外网；写 data/smd/）
python scripts/real_data/fetch_smd.py

# 2. 求值方式分析：level vs ratio vs delta（不需要 Laya，秒级）
python scripts/real_data/framing_smd.py machine-1-6

# 3. 两套 profile 的 A/B（约 12 分钟，4,708 窗口 × 2 臂）
python scripts/real_data/eval_smd.py --out data/smd/report_full.json

# 4. 只跑 3 指标子集（约 6 分钟）
python scripts/real_data/eval_smd.py --host-features cpu_r,load_1,mem_free --profiles host

# 5. 快速冒烟
python scripts/real_data/eval_smd.py --limit-calls 200
```

产出：`data/smd/report_full.json`、`report_subset.json`、`framing_machine-1-6.json`。

## 5. 因此要怎么改（按优先级）

1. **加长时程基线，或改判据。** 当前 30 窗滚动基线会吸收持续故障。至少需要一个"长窗参考"（例如同机同时段历史分位、或 24h–7d 的稳健区间），让"持续偏高"仍然构成偏离。
2. **状态里必须显式陈述绝对水平与稳定参考区间。** 3.1 已经证明：水平有信号（0.815），比值没有（0.493）。digest 应写 `CPU 0.20（历史区间 0.05–0.35，近 30 窗中位 0.19）` 这类"水平 + 参考"，而不是只写倍数。
3. **每个数据源要一套经过测量的 profile，且指标要精选。** `host` profile 已存在但按本次结果需要收缩到少数强信号（3 指标 0.692 > 8 指标 0.515）；服务侧保持现有 2–3 个判别性指标。
4. **换域即重扫阈值与校准。** 在 SMD 上 0.5 阈值零触发；在合成 HTTP 场景上 0.5583（校准刻度）给出 recall 0.854 / FPR 0.000。两组阈值互不通用。
5. **明确适用范围：不要用 Laya 做单指标阈值能解决的问题。** 那类问题用阈值告警更便宜、更可解释、更容易审计。Laya 应该只用在"需要综合多个信号并给出类别/处置"的窗口上，且用 System 2 兜住。

## 6. 本次验证**没有**推翻的东西

- 合成 HTTP 场景上的结论仍然成立：recall 0.854 / FPR 0.000 / precision 1.000（`brian eval --repeat 6`），本次改动后已回归复验。
- 渲染器是模型参数这一结论，在 SMD 上再次得到独立印证（同一批数值，不同表述，AUC 0.52 ↔ 0.86 ↔ 0.90）。
- 两套 profile 必须是两套已测量的文本，不能合并：给 service profile 的资源行加基线，合成集 FPR 会从 0.000 跳到 1.000（已实测）。
- Kafka / Flink 仍然没有在真实集群上跑过（与本验证无关）。
