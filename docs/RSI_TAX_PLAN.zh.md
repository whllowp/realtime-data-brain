# 参考《The RSI Tax》的 10 轮优化

> 论文：[The RSI Tax: When Recursive Self-Improvement Is Not Worth the Cost](https://arxiv.org/html/2611.13524v1)
> （arXiv:2611.13524v1，Zhang / Li / Wang，CC BY 4.0）

## 论文说了什么（只摘与本项目相关的）

1. **RSI Tax**：自我改进过程的 token 成本必须计入端到端评估。端到端 = `N_task + N_RSI`，只报准确率而不计改进成本，会让昂贵的流程看起来免费。
2. **SRN 基线**：一个有界笔记（2,048 token，每 4 个任务用失败任务修订一次），在四个设置中三个准确率最高、一个并列，同时比 Meta-Harness / EvoSkill / RRSI 少用 **65.6–71.0%** 的总 token。
3. **成本分解**：`Verify`（在已完成任务上验证候选）、`Explore`（采样/提案）、`Write`（落盘状态）。三种 RSI 方法的验证开销占 RSI Tax 的 **74.8–93.6%**。
4. **未被使用的产物**：23.7–63.6% 的 RSI Tax 花在后续任务从未使用的状态/产物上。

## 映射到本项目（必须先说清楚，因为场景不同）

| 论文 | 本项目 |
|---|---|
| `N_task`（任务执行） | Laya 决策。本地固定模型，无 token，成本是 GPU 时间 |
| `N_RSI`（改进过程） | System 2：每个升级告警一次 LLM 调用。**这才是账单** |
| RSI Tax | **每决策的 token 数** |
| 未被使用的产物 | **挂在不会触达人的告警上的报告** |
| Verify / Explore / Write | 本项目每次报告只调用 1 次 LLM，因此是 **100% Write**，0 Verify，0 Explore |

单位从不混用：token 与毫秒分开报，比值只在同一单位内计算。

## 第 1 轮：把成本账建起来（此前完全没有）

### 1.1 发现：token 早就被计数，但从未进入评估

`LlmClient` 一直在累计 `prompt_tokens` / `completion_tokens`，`RcaEngine` 也有 `stats()`；
但 `eval.py`、`pipeline.py`、所有 10 轮 SMD 迭代**一次都没有读过**。这正是论文指出的记账失败：
昂贵的半边在账本之外。

### 1.2 落地

| 文件 | 改动 |
|---|---|
| `src/brian/contracts.py` | `RcaReport` 新增 `prompt_tokens` / `completion_tokens` / `estimated_prompt_tokens` |
| `src/brian/llm/rca.py` | LLM 路径填入实际 token；确定性路径填入**提示词估算值**（该估算器原本只用于超长告警） |
| `src/brian/pipeline.py` | `Counters` 累计 `rca_prompt_tokens` / `rca_completion_tokens` |
| `src/brian/cost.py` | `CostLedger`：按动作归因、论文口径的 Verify/Explore/Write 分解、unused share |
| `src/brian/cli.py` | 新增 `brian cost` |
| `tests/test_cost.py` | 7 个测试守护口径（不混单位、估算不覆盖真实账单、计数器路径不假装能归因） |

### 1.3 基线（合成流，35 窗口）

```
windows            35
laya decisions     35  (0.00 ms/window)
rca reports        8  (8 degraded)
tokens             31725  (prompt estimate; nothing billed - deterministic mode)
tokens / report    3965.6
tokens / window    906.4
split              verify 0  explore 0  write 31725  other 0
unused share       37.4%
by action:
  deep_analysis  reports 3    tokens 11854
  page_human     reports 5    tokens 19871
```

三个立刻可用的结论：

1. **单次分析约 3,966 token，每窗口 906 token** —— 这是 RSI Tax 的本项目版本。
2. **37.4% 的分析预算花在 `deep_analysis` 告警上**，那不是会把报告放到人面前的动作用。这是论文 unused-artifact 的对应量，且是**下界**（严格口径：只有 `page_human` 算"被使用"）。
3. **分解是 100% Write** —— 本项目没有验证与探索预算。论文里验证占了 74.8–93.6%，而这里是一次调用直接写报告。**结构上已经站在便宜的一侧**，这一点在"优化"之前必须先承认。

### 1.4 这一轮没有做的事

- 没有接真实 LLM 跑（需要 API key），所以 `tokens` 是**提示词估算**，明确标注。完成侧 token 无法离线估算。
- 没有动 `always_analyze_alerts`（当前为 True），那正是下一轮要测的旋钮。

## 第 2 轮：修正一个错误结论 + 按动作路由分析

### 2.1 先纠错：第 1 轮的"unused share"是错的

第 1 轮报"37.4% 的分析预算花在未被使用的产物上"。读动作阶梯的定义才发现**这是误判**：

| 动作 | 定义原文 | 报告是什么 |
|---|---|---|
| `auto_triage` | "confident System 1 judgement: **LLM writes the narrative**" | 交付物 |
| `deep_analysis` | "not confident enough to act on the class/severity: **the LLM must reason harder**" | 交付物 |
| `page_human` | "page a human in parallel with the LLM analysis" | 交付物 |

三者都需要报告，**没有一个是"产生后就被丢弃的产物"**。论文的 `r_no-use` 在本系统不成立。

指标已改名 `share_below_page`（不触达人的告警占比），并写明它**不是** `r_no-use`：
它衡量的是"从不打扰任何人的花销"，这正是"更便宜的叙述策略"该瞄准的部分，但不是"浪费"。

### 2.2 真正的机会：阶梯已经分好了需求程度

`auto_triage` 只要叙述，`deep_analysis` 要推理，`page_human` 两者都要。
为 `auto_triage` 付一次完整推理，正是论文测到的"不需要的验证"。于是新增
`GateThresholds.analyze_actions`（默认全部，保守），`brian cost` 可对比策略：

| 策略 | 计费报告 | tokens | 每窗口 | 相对现状 |
|---|---|---|---|---|
| **A 全部**（现状） | 8 | **31,725** | 906.4 | — |
| B `deep_analysis`+`page_human` | 8 | 31,725 | 906.4 | **0%** |
| **C 仅 `page_human`** | 5（+3 走规则） | **19,871** | 567.7 | **−37.4%** |

两个结果都要说清楚：

1. **B 省不到钱**，因为这条合成流里根本没有 `auto_triage` 告警——这是**流的属性，不是策略的失败**。
2. **C 省 37.4%，代价正是阶梯要求的推理**。`deep_analysis` 的字面意思就是"LLM 必须更深入推理"，
   把它路由到规则，等于用成本换掉那 3 个告警的推理质量。

所以 C 不是"优化"，是**一个需要运维判断的取舍**。论文的价值也在这里：把账单摆出来，让取舍是自觉的。

### 2.3 保证：跳过分析不等于静默

新增的 `RcaEngine.analyse_rules()` 让被路由掉的告警**仍然拿到报告**（确定性推理器写），
只是不计 token。没有这条，"省钱"会伪装成"少解释"——那才是真正的退化。

测试：`tests/test_analysis_routing.py`（解析容错、空集合合法、默认必须保守）。

## 第 3 轮：有界笔记（SRN 类比）——结论是它不省钱

### 3.1 先说清楚为什么直觉会错

论文里 SRN 省 65.6-71.0%，是因为它击败的三个方法把 **74.8-93.6%** 的预算花在**验证**上。
**本系统没有验证预算**：每次报告 1 次 LLM 调用、无候选搜索、无重打分。所以笔记在这里没有东西可替代，
它只能**额外增加**每个提示词的 token。这一点必须写在实验之前，否则会把"删证据省下的钱"记到笔记头上。

### 3.2 测量（8 个告警，合成流）

| 配置 | tokens/告警 | 合计 | 相对基线 |
|---|---|---|---|
| 基线（无笔记，20 事件） | 3,965.6 | 31,725 | — |
| 只加笔记（20 事件） | 4,079.2 | 32,634 | **+2.9%** |
| 笔记 + 少事件（4 条） | 2,619.8 | 20,958 | -33.9% |
| **只减事件（4 条，无笔记）** | 2,506.1 | 20,049 | **-36.8%** |

**决定性的是最后一行**：只删证据比"笔记+删证据"更省。省下的 36.8% 全部来自减少事件上下文，
笔记是净增加约 2.9%。

### 3.3 结论与处置

- 笔记**不接入默认路径**。`src/brian/notes.py` 作为能力保留（有界、可审计、可持久化），
  提示词里已有可选的 `note=` 入口，但默认不传。
- 若将来接入，它必须靠**质量**证明自己，而质量需要真实 LLM 才能测——本轮无法测。
- 真正被证明有效的是**事件上下文条数**：4 条比 20 条省 36.8%。但那是"少给证据"，
  不是"更聪明的证据"，所以下一步必须先测质量代价，而不是继续加笔记。

## 第 4 轮：证据裁剪的代价，以及一个真正有效的修正

### 4.1 第 3 轮那个 36.8% 不是免费的

把事件上下文按“最近 N 条”砍到 4 条，实测证据保留率：

| 砍到 | 日志保留 | 签名保留 | 首个错误 | 部署/配置 |
|---|---|---|---|---|
| 4 | **23%** | **38%** | **0%** | 88% |
| 8 | 45% | 60% | **0%** | 88% |
| 20 | 100% | 100% | 100% | 100% |

砍到 4 条丢掉四分之三的日志证据，且**首个错误完全消失**。

### 4.2 问题在选择策略，不在预算

既然证据有高下之分，“只取最近”就是错的规则。
`build_rca_messages` 改为按诊断价值挑选（`select_events`）：

1. **上下文标记**（deploy / version / config_change / flag）优先——它们重新定义了其余测量的含义；
2. **日志事件**，且每个不同签名的**首次出现**优先（区分“刚开始”与“一直在”）；
3. 剩余预算用**最近的指标采样**填充。

渲染仍按时间排序：分组决定*哪些*事件存活，不改变展示顺序。

### 4.3 改善后的对比

| 事件数 | tokens/告警 | 合计 | 相对 20 条 | 证据保留 |
|---|---|---|---|---|
| 20 | 3,972 | 31,776 | — | 100% |
| **8** | **2,738** | **21,905** | **-31.1%** | **100%** |
| 4 | 2,344 | 18,752 | -41.0% | 95% |

**砍到 8 条：省 31.1% 且证据零损失**。这是对比第 3 轮“砍到 4 条省 36.8%”
更好的交换：差不多的省钱，但不拿证据去换。

### 4.4 结论

- 默认 `max_events=20` **不变**（选择函数在 20 条时是恒等的，不改变现有行为）。
- 推荐配置：`BRIAN_LLM_MAX_CONTEXT_EVENTS=8`。
- 重要的不是“少给证据”，而是**先给对的证据**——同一份 8 条，
  按时间挑选丢失 55% 日志，按诊断挑选丢失 0%。

## 第 5 轮：没有“贵类别”，钱在提示词的固定结构里

### 5.1 按类别归因：完全扁平

给账本加了 `by_category`（用 **预测**类别，不是场景标签——那才是生产环境真正拥有的信息）：

| 类别 | 报告数 | tokens | 每报告 | 相对中位数 |
|---|---|---|---|---|
| security | 1 | 4,072 | 4,072 | 1.0x |
| data_quality | 1 | 4,044 | 4,044 | 1.0x |
| config_or_deploy | 1 | 4,023 | 4,023 | 1.0x |
| resource_exhaustion | 4 | 15,830 | 3,958 | 1.0x |
| none | 1 | 3,807 | 3,807 | 0.9x |

**没有任何一个类别的单份成本显著偏高**。账单由提示词的固定结构决定，与事故类型无关。
因此“给贵类别做定制”这条路不存在，优化必须靠提示词本身。

### 5.2 拆解提示词：事件与固定块各占一半

| 部分 | tokens/告警 | 占比 |
|---|---|---|
| 事件块（20 条） | 1,838 | 46% |
| 固定块（判决 + 窗口摘要 + 指标 JSON） | 2,134 | 54% |
| 其中：指标 JSON | ~1,271 | 32% |
| 其中：系统指令文本 | ~378 | 10% |

第 4 轮的事件策略只能碰到 46%。剩下 54% 是每个告警的地板。

### 5.3 一个白拿的 8%：指标 JSON 不该缩进

`json.dumps(..., indent=1)` 在每个告警上花了 ~317 token 的空白，而模型不需要缩进。

| 配置 | 字符数 | ~tokens |
|---|---|---|
| `indent=1`（原） | 5,084 | 1,271 |
| 紧凑分隔符（现） | 3,818 | 954 |

同一份 JSON，信息零损失，**-8%**。

### 5.4 累计效果（都是零信息损失）

| 阶段 | tokens/告警 | 相对初始 |
|---|---|---|
| 初始（20 事件 + 缩进 JSON） | 3,972 | — |
| 20 事件 + 紧凑 JSON | 3,655 | -8.0% |
| **8 事件 + 紧凑 JSON** | **2,421** | **-39.0%** |

第 4 轮已证明 8 条事件的证据保留率是 100%，紧凑 JSON 不改任何内容——
所以这 39% 是**真正白拿的**，不是拿证据换的。

### 5.5 剩下的地板

8 事件时还有 1,818 tokens/告警 是固定块。其中系统指令 ~378，指标 JSON ~954，
余下是判决与窗口摘要。再往下砍就要动“给模型看什么”，而不是“看多少”，
那属于质量取舍，已超出本轮能验证的范围。

## 第 6 轮：与阈值法对比，以及一个必须说清楚的结构事实

### 6.1 结构事实：System 2 不参与检测

`process_digest` 的顺序是固定的：发布 digest → Laya 判定 → 门控 → **发布决策** → 发布告警 → System 2 推理。

因此：**System 2 的 token 无法改变 recall 或 FPR**——它运行时判定已经落库。
这意味着任何“LLM 在检测上赚回了成本”的说法，都是把 Laya 的功劳算到 LLM 头上。

费用只能由**解释质量**辩护，而解释质量需要真实模型（甚至人工）才能评估。

### 6.2 同窗口、同误报预算下的检测对比（合成流，35 窗口 / 8 异常）

| detector | recall | FPR |
|---|---|---|
| 阈值：错误率 | **无可用操作点** | — |
| 阈值：延迟 p99 | **无可用操作点** | — |
| 阈值：CPU | **无可用操作点** | — |
| **Laya（扫点）** | **0.875** | **0.000** |
| Laya @0.5 | 0.875 | 0.037 |

“无可用操作点”是实测结果：在 10% 误报预算内，这三个单信号阈值找不到任何能捕获事件的切点。

### 6.3 与真实数据相反，而这正是重点

| 数据 | 模型 | 单指标阈值 |
|---|---|---|
| 合成流（35 窗口） | **recall 0.875 / FPR 0.000** | 无可用操作点 |
| RCAEval 服务侧（3,064 窗口） | AUC 0.44–0.51 | **AUC 0.75–1.00** |
| SMD 主机侧（4,708 窗口） | AUC 0.745 | **0.904** |

合成数据上模型完胜，真实数据上阈值完胜。
这不是矛盾，而是**合成场景是我自己写的**这个事实的直接体现：
异常里同时有错误、延迟、资源三重信号，模型只要识别“这种组合”就行；
真实注入故障往往只有一个指标异常，正好落在阈值的主场。

### 6.4 成本（单位不混）

| 项 | 数值 | 每 1,000 窗口 |
|---|---|---|
| Laya 决策 | 35 | 1,000 |
| System 2 报告 | 8 | 229 |
| System 2 tokens | 28,960 | 827,429 |
| 阈值检测器 | 0 tokens / 0 调用 | 0 |

**229 个告警/千窗口，每个告警 ~3,620 token。** 这就是这套架构的真实单价。
